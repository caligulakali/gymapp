# ARCHITECTURE.md — Архитектура проекта и эталон код-ревью

Этот документ — эталон архитектуры, по которому Code Reviewer проводит
код-ревью. Правила процесса и роли — в `AGENTS.md`, требования — в
`PROJECT_SPEC.md`. Отклонения от этого документа допустимы только
с согласия пользователя и фиксируются здесь.

## 1. Стек (база)

- TypeScript + React + Vite — интерфейс и сборка.
- PWA: `vite-plugin-pwa` (manifest, service worker, offline).
- Локальная БД: IndexedDB через Dexie.js.
- Тесты: Vitest (unit) + Testing Library (компоненты).
- Экспорт: JSON, CSV, собственный формат `.gymapp`.

## 2. Слои и зависимости

```
tests/  →  ui/  →  domain/  →  db/  →  IndexedDB
```

- `db/` — доступ к IndexedDB: схема Dexie, сущности, миграции версий,
  транзакции записи/чтения. Не знает о UI.
- `domain/` — бизнес-логика: упражнения, шаблоны, тренировки,
  экспорт/импорт, аналитика. Чистые функции, без обращения к DOM/IndexedDB
  (зависимости передаются).
- `ui/` — страницы, компоненты, хуки, стили. Не обращается к IndexedDB
  напрямую — только через `domain/` и `db/`.
- `tests/` — unit (db/domain), компонентные (ui), зеркалит слои кода.

Правила зависимостей: запрещены циклические импорты; `domain/` и `db/`
не импортируют из `ui/`; `db/` не импортирует из `domain/` и `ui/` (кроме
общих типов сущностей в `db/`).

## 3. Модель данных (упрощённая)

- `Exercise`: `id`, `name`, `muscleGroup`, `type`
  (`strength` | `cardio` | `time` | `reps`), `unit` (`kg` | `lb`),
  `notes?`, `favourite?`.
- `Template`: `id`, `name`, `notes?`,
  `exercises: [{ exerciseId, order, sets, targetReps?, targetWeight? }]`.
- `Workout`: `id`, `templateId?`, `date`, `notes?`,
  `exercises: [{ exerciseId, order, sets: [{ weight?, reps?, time?, distance?, rest? }] }]`.
- Общие правила: идентификаторы стабильны и сохраняются при импорте;
  даты хранятся в ISO 8601 UTC; отображение — локальное время.

## 4. Экспорт и импорт

- Чистые функции в `domain/`: вход — сущности, выход — файл (строка/Blob).
- `.gymapp` — JSON с полями `format: "gymapp"`, `version`,
  `exportedAt`, `exercises`, `templates`, `workouts`.
- JSON — полная копия данных; CSV — табличное представление.
- Импорт: валидация схемы → миграция старой версии формата → проверка
  конфликтов id → атомарная запись транзакцией → отчёт об ошибках.
- Чужой/вредоносный файл не ломает базу; импорт старых версий корректен.
- Обязательный тест round-trip: «экспорт → импорт» возвращает те же данные.

## 5. PWA

- Service worker кэширует только статику сборки, никогда — данные
  пользователя (IndexedDB не попадает в кэш SW).
- Установка, manifest и офлайн-работа — по настройке `vite-plugin-pwa`.

## 6. Стандарты кода

- Строгий TypeScript, `noImplicitAny`; `any` запрещён (исключения —
  с комментарием «почему»).
- Именование: `camelCase` — функции/переменные, `PascalCase` — типы
  и компоненты, `kebab-case` — файлы, `UPPER_SNAKE_CASE` — константы.
- React: функциональные компоненты, хуки (`use*`), переиспользование
  компонентов, типизированные props.
- Комментарии объясняют «почему», не «что». Без мёртвого кода,
  без дублей (DRY), без `console.log` в продакшене.
- Безопасность: экранирование пользовательского ввода (без
  `dangerouslySetInnerHTML` без обоснования), валидация импортируемых
  данных.

## 7. Тестирование

- Критические системы обязаны иметь тесты: хранение/миграции БД, логика
  упражнений/шаблонов/тренировок, экспорт/импорт (round-trip), аналитика,
  ключевые сценарии UI.
- Тесты не зависят от сети и времени суток (инъекция дат).
- Покрытие критических путей — не ниже 80%.

## 8. Чек-лист код-ревью

### Архитектура
- [ ] `ui/` не обращается к IndexedDB напрямую.
- [ ] Слои не имеют циклических зависимостей, соблюдена направленность.
- [ ] Экспорт/импорт — чистые функции, без побочных эффектов в UI.
- [ ] Миграции схемы БД предусмотрены (бамп версии Dexie).
- [ ] Service worker кэширует только статику, не данные пользователя.
- [ ] Все данные локальны, сетевых отправок нет.

### Чистота кода
- [ ] Строгая типизация, нет `any` без обоснования.
- [ ] Соблюдены соглашения именования.
- [ ] Нет мёртвого кода, дублей, неиспользуемых импортов.
- [ ] Комментарии только «почему».
- [ ] Компоненты разделены по ответственности, props типизированы.

### Соответствие ТЗ
- [ ] Функциональность соответствует `PROJECT_SPEC.md` (стадия 1).
- [ ] Нет известных незакрытых багов и недоработок списка требований.

### Тесты
- [ ] Критические пути покрыты тестами (не ниже 80%).
- [ ] Тесты не зависят от времени суток и сети.
- [ ] Round-trip экспорта/импорта покрыт.

### Заключение
- `approve` — замечаний нет или они не блокирующие.
- `changes requested` — перечень замечаний по файлам и строкам,
  после исправления — повторное ревью.
