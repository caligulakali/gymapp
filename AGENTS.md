# AGENTS.md — Архитектура и правила работы ИИ-агентов

Этот файл — обязательная база (промт) для всех ИИ-агентов, работающих
над проектом. ТЗ (суть проекта) — в `PROJECT_SPEC.md`, эталон архитектуры
для код-ревью — в `ARCHITECTURE.md`. Агент, который не прочитал все
три файла перед началом работы, не должен начинать работу.

## 1. Роли агентов

| Роль | Кто | Чем занимается |
|------|-----|----------------|
| Developer | основной агент | Пишет код, тесты, коммиты |
| Code Reviewer | отдельный независимый агент | Проверяет код после ручной проверки |
| Test Reviewer | отдельный независимый агент | Проверяет тесты до написания кода |
| Security Reviewer | отдельный независимый агент | Ревью безопасности |

Каждая роль-ревью выполняется **отдельным агентом**, который не писал
проверяемый код.

## 2. Обязательный процесс каждой задачи

1. **Цель.** Агент берёт задачу из `PROJECT_SPEC.md` (стадия 1) и уточняет
   у пользователя детали, если чего-то не хватает.
2. **Ветка.** Создаётся отдельная ветка для задачи
   (см. правила Git ниже). В `main`/`master` напрямую ничего не коммитится.
3. **Тесты ДО кода (TDD).** Для всех важных (критических) систем агентом
   пишутся тесты ПЕРЕД написанием кода. Тесты описывают требуемое поведение.
4. **Ревью тестов (Test Reviewer).** Тесты проходят ревью отдельным
   агентом до написания реализации. Замечания исправляются.
5. **Код.** Реализация, закрывающая тесты. Код пишет только агент.
6. **Коммиты.** Агент сам делает осмысленные коммиты своей работы.
7. **Ручная проверка пользователем.** Пользователь сам «клацает» новую
   фичу руками и проверяет её. Агент ждёт решения: принято / замечания.
8. **Код-ревью (Code Reviewer).** После успешной ручной проверки отдельный
   независимый агент проверяет код на:
   - соблюдение архитектуры (`AGENTS.md` и `ARCHITECTURE.md`);
   - чистоту кода (стиль, дублирование, читаемость);
   - соответствие ТЗ (`PROJECT_SPEC.md`);
   - покрытие тестами.
   Замечания устраняются, при необходимости — повторное ревью.
9. **Повторная ручная проверка.** После код-ревью пользователь снова
   проверяет результат руками.
10. **Ревью безопасности (Security Reviewer).** Отдельным агентом
    проверяется: отсутствие XSS, безопасная обработка данных, экспорт без
    утечек, безопасность service worker и хранилища. Замечания устраняются.
11. **Завершение.** Задача считается готовой только после всех ревью
    и ручных проверок. Обновляется чек-лист в шапке PR/ветки.

## 3. Git-правила

- Каждая задача — **отдельная ветка**: `feature/<краткое-название>`.
- Ветки создаёт и коммиты делает агент.
- После создания коммитов агент сам отправляет рабочую feature-ветку в
  удалённый репозиторий (`git push -u origin feature/<краткое-название>`),
  если пользователь явно не попросил работать только локально.
- **Агент НЕ сливает (merge) ветки сам.**
- Агент не отправляет коммиты напрямую в `main`/`master` и не выполняет
  push этих веток. Слияние в основную ветку выполняет только пользователь.
- Слияние в основную ветку выполняет только пользователь после своей
  ручной проверки.
- Когда работа, для которой создана feature-ветка, завершена, агент обязан
  явно запросить у пользователя разрешение на слияние этой ветки в `main`.
  До получения такого разрешения агент не выполняет merge и не считает
  задачу полностью завершённой.
- Коммиты: атомарные, осмысленные сообщения, одно логическое изменение
  на коммит. Типы: `feat:`, `fix:`, `test:`, `refactor:`, `docs:`, `chore:`.
- Не коммитить: секреты, ключи, личные данные, лишние бинарные файлы.

## 4. Архитектура проекта (база)

- **Стек (начальное предложение, менять только с согласия пользователя):**
  - TypeScript + React + Vite — интерфейс и сборка;
  - PWA: `vite-plugin-pwa` (manifest, service worker, offline);
  - локальная БД: IndexedDB через Dexie.js;
  - тесты: Vitest (unit) + Testing Library (компоненты);
  - экспорт: JSON, CSV, собственный формат `.gymapp`.
- **Слои кода:**
  - `db/` — доступ к IndexedDB, сущности, миграции схемы;
  - `domain/` — бизнес-логика: упражнения, шаблоны, тренировки,
    экспорт/импорт, аналитика;
  - `ui/` — компоненты интерфейса, страницы, стили;
  - `tests/` — тесты всех уровней по структуре слоёв.
- Слой `ui/` не обращается к IndexedDB напрямую — только через `db/`
  и `domain/`.
- Экспорт/импорт — функции чистого типа: вход — сущности, выход — файл,
  без побочных эффектов в UI.
- Все данные локальны. Никаких сетевых запросов с данными пользователя.

## 5. Стандарты кода

- TypeScript, строгая типизация, без `any` (исключения — с комментарием).
- Именование: `camelCase` для функций/переменных, `PascalCase` для
  типов/компонентов, `kebab-case` для файлов.
- Комментарии в коде — только на английском языке. Комментарии объясняют
  «почему», не «что».
- Без мёртвого кода: удалять неиспользуемое сразу.
- Одна ответственность на модуль/компонент, переиспользование общего.
- Зависимости добавляются только при необходимости, с проверкой.

## 6. Тестирование

- Критические системы (обязательно тесты ДО кода):
  - хранение данных (IndexedDB): запись, чтение, миграции, целостность;
  - логика упражнений, шаблонов, тренировок (создание, изменение, удаление);
  - экспорт (JSON/CSV/`.gymapp`) и импорт: round-trip «экспорт → импорт»
    возвращает те же данные;
  - аналитика прогресса (расчёты корректны);
  - ключевые сценарии UI (запись тренировки, редактирование).
- Тесты не зависят от реальной сети и от времени суток (использовать
  инъекцию дат).
- Покрытие критических путей — не ниже 80%.
- Тесты проходят ревью Test Reviewer'ом ДО реализации.

## 7. Безопасность

- Никакой обработки чужих данных, всё локально.
- Экспортируемые файлы не содержат лишнего (секретов, скрытых полей).
- Валидация при импорте: чужие/вредоносные файлы не ломают базу,
  импорт старых версий формата корректен.
- Риски XSS в отображаемых пользовательских данных (названия упражнений,
  заметки) — обрабатывать: экранирование при вставке в HTML.
- Service worker кэширует только статику приложения, не данные пользователя.
- Ревью безопасности выполняет отдельный агент (Security Reviewer).

## 8. Запрещено агентам

- Не делать ревью собственного кода само за себя — ревью выполняет
  другой агент.
- Не сливать ветки и не пушить в основную ветку напрямую.
- Не писать код без тестов для критических систем.
- Не отправлять данные пользователя куда-либо.
- Не брать задачу, не прочитав `PROJECT_SPEC.md` и этот файл.
- Не приступать к следующей задаче, пока текущая не прошла полный цикл
  (ручная проверка → ревью → ручная проверка → ревью безопасности).
